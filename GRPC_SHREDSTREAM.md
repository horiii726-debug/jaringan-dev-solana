# ShredStream gRPC — how it works, how data is collected, what comes out

Latest numbers: [data/shred/GRPC_RESULTS.md](data/shred/GRPC_RESULTS.md) (regenerated by `bash grpc_report.sh`).

## 1. Goal
See Pump.fun coins **at the moment they are created** (before they show up on the Pump.fun website or DexScreener)
and check whether the creator is on our watchlist (quality creators / dev families). Current mode: **paper**
(record only; no wallet keys, no transactions sent).

## 2. Data sources
| Source | Status | Notes |
|---|---|---|
| **AllenHark Shared gRPC** (address = `ALLENHARK_GRPC` in `.allenhark.env`) | **RUNNING** | Plaintext gRPC (h2c), header `x-api-key`, Frankfurt. Key lives in `.allenhark.env` on the server (never committed). The server IP must be whitelisted in the AllenHark dashboard. |
| ShredStream.com Raw UDP (Frankfurt) | not usable | The vast.ai server only exposes TCP ports; UDP packets to `62.107.25.205:8001` are dropped before they arrive (`udpprobe` logged 0 packets). Needs a VPS with open UDP. |
| Plain Helius RPC (WebSocket) | baseline | Measured on 18 Nov: median ~2.6 s behind. |

## 3. Pipeline (program `shredrx/`, Rust)
1. **Connect** to `/shredstream.ShredstreamProxy/SubscribeEntries` (Jito ShredStream protocol). The server streams
   messages continuously; each message = part of one slot (`slot` + bincode-encoded `entries`).
2. **Decode** `entries` into transactions. Legacy / v0 Solana transactions are fully decoded (accounts, instructions).
   Most messages contain the **new Solana transaction format (first byte 0x81)**, which is not fully decoded yet;
   for those messages a **fallback** scans the raw bytes for Pump.fun create instruction data.
3. **Detect coin creation**: Pump.fun program `6EF8rrecthR5Dkzon8Nwu78hRvfCKubJ14M5uBEwF6P`, discriminator
   `create` `[24,30,200,40,5,28,7,119]` or `create_v2` `[214,144,76,236,95,139,49,180]`.
   Read: name, symbol, URI, **creator** (argument), mint (account #0), user (account #7 create / #5 create_v2).
4. **Watchlist match**: creator / user / fee payer looked up in `data/v3/reput/watchlist.json` (reloaded every 60 s).
   A match goes to `hits.jsonl`.
5. **New wallets funded by a parent**: a SOL transfer >= 0.05 from a watchlist wallet to a new wallet puts that
   wallet on the watch list (`dynamic_watch.jsonl`), because 78% of creators use one-time wallets funded by a parent.
   (Currently only seen in legacy / v0 transactions.)
6. **Measure the rise** (`jaringan streamrise`, afterwards): for each coin the mint is resolved (if missing) from
   the creator's create transaction closest in time to the stream, then all bonding-curve trades are read (Helius):
   first price we could have bought (slot after the create), peak, last price, graduated or not.

## 4. Output files (`data/shred/`)
| File | One row = |
|---|---|
| `creates.jsonl` | a new coin: `t_ms` (our receive time, ms), `slot`, `ix` (create/create_v2), `parse` (`scan` = fallback), `mint`, `creator`, `user`, `payer`, `name`, `symbol`, `hit` (filled when it matches the watchlist) |
| `hits.jsonl` | new coins created by watchlist wallets (same format) |
| `dynamic_watch.jsonl` | new wallets funded by a watchlist wallet: `from`, `from_role`, `wallet`, `sol`, `entitas` |
| `rise/rise.jsonl` | rise per coin: `mint`, `symbol`, `creator`, `delay_ms` (our delay vs block time), `n_trades`, `graduated`, `x_entry` (peak / entry price), `x_launch` (peak / Pump.fun start price), `last_vs_entry`, `peak_after_s`, `peak_mcap_sol` |
| `rx.log` | stats every 10 s: messages, transactions, creates, hits, fallback count, MB, watched wallets |
| `probe.log` | ShredStream.com UDP test (packets received) |

## 5. Running
```
bash start_shredrx.sh                                                                     # gRPC receiver (background)
JAR_RPS=3 ./target/release/jaringan streamrise data/shred/creates.jsonl data/shred/rise 5   # measure rises
bash grpc_report.sh                                                                       # rewrite data/shred/GRPC_RESULTS.md
```

## 6. Known limits
- The mint of new-format (0x81) transactions is not decoded directly; it is resolved later via RPC.
- Parent -> new wallet transfers are not seen in new-format transactions yet.
- Solana block time has 1-second resolution, so `delay_ms` is uncertain by up to ~1 s.
- No buying yet (paper); "entry" = first trade in the slot after the create, not our own fill.
- The AllenHark / ShredStream trials end on 21 Nov 2026; longer use needs a paid plan.
